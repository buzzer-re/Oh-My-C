# Tools

Tools are `agent_tool_t` objects (`src/agent/agent.h`): name, label, description, JSON Schema
`parameters`, an `execute` function, and flags (`exclusive`, `hidden`, `discoverable`, `mounted`,
`intent_mode`, `examples`). The built-ins live in `src/tools/` and share a per-session `tool_env_t`
(`src/tools/tools.h`): cwd, hashline snapshot store, todo state, persistent shell, jobs, artifact
store, discovery results, and callbacks into the session (subagents, completions, eval bridge,
plan proposals, UI `ask`). Per-tool completeness is tracked in [status.md](status.md) (Tools).

## Registration and wire parity

- `tools_register_builtin()` (`tools_common.c`) constructs the enabled built-ins. Gating follows
  omp's `resolveBuiltinToolPlan()`: `bash.enabled`, `todo.enabled`, `glob.enabled`,
  `grep.enabled`, `astGrep.enabled` (off), `astEdit.enabled`, `web_search.enabled`, `ask.enabled`
  (needs a UI), `find.enabled` (`auto` follows the judge role: on when it resolves first to a native judgment backend),
  `wait` (needs jobs), and `task` (depth below `task.maxRecursionDepth`). `--tools a,b` restricts
  the set, and `--no-tools` removes it.
- `install_agent()` (`coding/app.c`) adds the session-level tools: `lsp`, `debug`,
  `checkpoint`/`rewind`, `goal`, `learn`/`manage_skill`, MCP tools, and host tools.
- `tools_finalize()` sorts tools into omp's canonical `BUILTIN_TOOLS` order and mounts
  discoverable tools under `xd://`. The model therefore sees the same tool list, order and
  descriptions as omp.
- Descriptions are omp's markdown (`prompts/coding-agent/prompts/tools/<name>.md`, rendered by
  `tool_prompt()`, `omp://` → `omc://`). Schemas are omp's exact wire schemas written as JSON
  literals (`schema_lit`), including `additionalProperties`. The `i` intent field is injected
  separately ([agent.md](agent.md#the-intent-field-i)). `tests/parity/request_diff.sh` diffs the
  whole request against omp.

## `xd://` tool devices (`tools/xdev.c`)

This ports `tools/xdev.ts` and `internal-urls/xd-protocol.ts`. With `tools.commands` on (the default; `tools.xdev` before omp v19)
and both `read` and `write` present, *discoverable* tools are taken off the request's top-level tool
list and driven through files:

| Operation | Effect |
|---|---|
| `read xd://` | list mounted devices with one-line summaries |
| `read xd://<tool>` | docs plus the parameter schema rendered as a TypeScript type (`type Args = {...}`) |
| `read xd://<tool>/<topic>` | named doc topics (for example `xd://eval/judge`, `xd://eval/helpers`) |
| `write xd://<tool>` | run the tool. `content` is the JSON arguments object, validated like a normal call |
| `write xd://report_issue` | automated-QA report, recorded locally to `autoqa.jsonl` after consent and never sent anywhere |
| `write xd://propose` | plan-mode approval ([agent.md](agent.md#plan-mode)) |
| `write xd://resolve`, `xd://reject` | finish a staged `ast_edit` |

The default mounts are `ast_grep`, `ast_edit`, `debug`, `lsp`, `checkpoint`, `rewind`, `generate_image` and MCP tools.
`todo`, `ask`, `grep`, `web_search`, `read` and `write` stay top-level (omp's
`XDEV_KEEP_TOP_LEVEL`), as does any tool named explicitly in `--tools`. The system prompt carries the
device catalog or inline docs (`tools.commandDocs`, `tools.commandInline`); mounted MCP tools are listed once, in the
`## MCP Tool Routes` append part with their catalog summary. When the mounted set changes mid-session
(`coding/xdnotice.c`) the UI shows `xdev: xd://: mounted …; unmounted …` (`tools.commandNotices`) and the next user prompt
carries a hidden `xdev-mount-notice` naming the net change the model has not seen yet.

`read_execute()`, `tool_resolve_path()` / `tool_resolve_internal_url()` (`tools_common.c`) and
`tools/vurl.c`. The system prompt's "Internal URLs" section is generated by `internal_url_docs()`
from omp's `prompts/internal-urls/*.md`, listing only what the session can serve.

|---|---|---|---|

| `rule://<name>` | `read.c` (`read_rule`) | the rule body without its frontmatter (virtual resource) | `rule-protocol.ts` |
| `artifact://<id>[:sel]` | `tools_common.c`, `artifacts.c` | full output of a truncated tool call | `artifact-protocol.ts` |
| `local://<path>` | `tool_resolve_path` | per-session scratch dir `<session dir>/<id>/local` (plans live here); paths clamped to the root; read/write/edit | `local-protocol.ts` |
| `memory://root[/…]` | `coding/memory.c` | local-backend memory files | `memory-protocol.ts` |
| `agent://<id>[/json/path]`, `agent://all` | `read.c`, `vurl.c`, `coding/agents.c` | subagent outputs (a published, current `<id>.md` is located; JSON paths, progress and superseded outputs render through `vurl.c`); `write` sends a peer message | `agent-protocol.ts` |

| `attachment://N` | `coding/imgattach.c`, `tools_common.c` | the file behind the newest message's `Image #N` (the attachment notice's path, else a session blob) | `attachment-protocol.ts` |
| `pr://[owner/repo/]N[/diff[/i\|all]]`, `issue://[owner/repo/]N` | `tools/github.c` | GitHub REST; repo defaults to the cwd's github.com remote; token from `GITHUB_TOKEN`, `GH_TOKEN` or `gh` | `issue-pr-protocol.ts` |
| `ssh://[user@]host[:port]/path` | `tools/ssh.c` | remote UTF-8 text (≤1 MiB) and directory listings through OpenSSH (ControlMaster, `BatchMode=yes`, hosts from `ssh.json`); byte-exact staged writes; read/write/edit | `ssh-protocol.ts` |
| `out://` | `out_url.c` (`iurl.h`) | write-only mid-turn reply to the user (`Shown to the user.`; ≤64 KiB; `cmd > out://` redirects in bash become `details.replies`); on where `out.enabled` says, unset = top-level interactive TUI only; never for subagents | `out-protocol.ts` |
| `cfg://[namespace\|setting][/save]` | `cfg_url.c` | settings view over omp's registry (`assets/config/settings-registry.json`): tree, namespace, setting detail with source; writes need the top-level TUI and the user's approval (runtime override, `/save` → config.yml) | `cfg-protocol.ts` |
| `conflict://N[/ours\|theirs\|base]`, `conflict://*` | `conflict.c` | git conflict blocks registered by `read` (window footer, `<path>:conflicts` index); `write` splices the block (`@ours`/`@theirs`/`@base`/`@both`) | `conflict-protocol.ts` |
| `omc://[doc]` | `read.c` | the embedded README and `docs/*.md` (omp's `omp://`) | `omp-protocol.ts` |
| `xd://…` | `xdev.c` | tool devices (above) | `xd-protocol.ts` |
| `http(s)://…` | `tools/web.c` | page as reader markdown, `:raw` for the original | `tools/read.ts` URL path |
| `file://…` | `tool_resolve_path` | plain path | |

**Located reads** (omp `read.ts` `LocatedRead`). A file-backed scheme (`skill://`, `artifact://`, `memory://`,
`agent://` with a published output, `attachment://`, `local://`) resolves to its backing file and `read_located()`
reads that file through the filesystem pipeline (`read_path()`) under the URL's identity, with the scheme's spec:

- *immutable* (all but `local://`): no hashline header or `N:` anchors (`resolveFileDisplayMode({immutable})`; line
  numbers only with `readLineNumbers`), no conflict scan; a file over 50 KB gets the `[Backing file: … Use <url>:raw:1-3000
  …]` notice, and a bare `:raw` of one is refused with omp's `Unbounded raw read blocked for <url> …` notice.
- *unbounded* (`skill://`): read whole through the in-memory builder (entity `file`, no summary, no result limits,
  `[N more lines in file. Use :N to continue]`); a non-`:raw` read starts with `[Skill file: <backing path>]`.
- *artifactStore* (`artifact://`): pages keep the full page budget and are never spilled.
- in-body hints (`Line N is beyond end of file … Use <url>:1 …`, `more lines in file`, budget / omitted-line notices,
  the column-cap selector) name the URL; the summary footer names it too.
- details: `meta.source = {type: internal, value: <url>}`, `contentType: text/markdown` for a Markdown backing file,
  `resolvedPath`, `displayContent` / `rowPrefixes` / `fileSize` / `truncation`, and `displayTarget` for `memory://` and
  `local://`, in omp's key order.

`rule://` and `omc://` are virtual resources paged by the in-memory builder (`[N more lines in resource …]`, details
`{resolvedPath?, contentType, totalLines, rowPrefixes, displayContent, meta.source}`). In the TUI, every read that
renders full (an internal URL, a Markdown resource) is omp's `readToolRenderer` card (`tc_files.c` `read_full_card`):
a Markdown cell or a code cell numbered from `displayContent`, an Output section with `⟦Resolved path: …⟧` and the
truncation warning, and a framed `✘ Read <url>` card for an error. Not ported: tree-sitter block context (omp shows
`…` plus the enclosing block's closing line around a partial window), the `history://` transcript renderer and its
hashline-numbered output, `omp://` as an alias of `omc://`, and the routed `proc://` / `cfg://` read cards.

## Tool approval

`tools/approval.c` ports omp's `tools/approval.ts`, `approval-cache.ts`, `approval-targets.ts`,
`search-approval-targets.ts`, every tool's `approval` / `formatApprovalDetails` / `approvalCacheTargets`
declaration and the bash approval patterns. The gate itself is `hook_approve_tool` in `coding/app.c`
(omp's `ExtensionToolWrapper.execute`): the agent loop calls it through the `approve_tool` hook once the
arguments validated, right before the tool runs, so the user approves exactly what executes.

**Resolution** (`approval_resolve`, omp `resolveApproval`): the tool's own decision (tier `read` /
`write` / `exec`, optional policy, override, reason, policy key), then the user's
`tools.approval.<tool>` (`allow` / `prompt` / `deny`, case-folded), then the mode
(`tools.approvalMode`: `always-ask` and `always-ask-cached` approve read, `write` read+write, `yolo`
everything; default `yolo`), then `tools.restrictedFolders`, which turns any non-deny result into a
per-call prompt. In yolo a tool's override prompt (critical bash) is ignored; a tool's own deny
(`skill://` writes: "`<scheme>:// URLs are read-only`") and a user deny win everywhere.
`--auto-approve` / `--yolo` force yolo; `--approval-mode <mode>` is a runtime override.

| Tool | Tier |
|---|---|
| `read` | read (an `ssh://` path, or a legacy PDF image member `x.pdf:page2.png`: exec) |
| `write` | the target's write tier: plain path write, `local://`/`agent://`/`out://` read, `cfg://`/`conflict://`/`vault://` write, `proc://`/`ssh://` exec, `xd://<device>` the device's own tier under policy key `<device>` (`resolve`/`reject`/`propose` read, `report_issue` write), other registered schemes deny |
| `edit`, `ast_edit` | the strictest write tier over every target (and move destination) |
| `bash` | exec; `bash.patterns` (`*` globs: `allow` must match the whole command without shell control, `deny`/`prompt` any segment, with a `deny` on any segment outranking another segment's `prompt`; operator (non-project) `deny`/`prompt` rules outrank a project-layer `allow`; an `allow` also matches after leading `NAME=value` assignments whose exact names its `env` list or `bash.allowedEnvVars` names, and `deny`/`prompt` segments match with or without leading assignments; a `prompt` rule's reason wins over a critical pattern; project and `--config` overlay lists prepend onto the global one, `[]` resets, runtime overrides replace; entries with `path`/`paths`/`pathPrefix`/`pathPrefixes` apply only under that tree, inline or through nested `patterns`/`values`/`items`), the critical patterns (`rm -rf /`, `sudo rm`, `curl … \| sh`, `mkfs`, `dd of=/dev/…`, fork bomb, `reboot`, `nc -e`, …) |
| `grep`, `glob`, `ast_grep`, `find` | read (exec when a path names `ssh://`) |
| `github`, `debug`, `lsp` | read for their read-only ops/actions, else exec (`lsp`: write) |
| `goal` (`get`), `learn` (project scope, no local backend), `todo`, `ask`, `wait`, `checkpoint`, `rewind`, `web_search` | read |
| `goal`, `learn` (global / skill / local backend), `manage_skill`, MCP tools | write |
| `eval`, `task` and any tool that declares nothing | exec |

**Prompting**: a call that resolves to `prompt` asks through `tool_env.ui.approve` (the TUI dialog,
`ui/approval.c`). Without a UI (print mode, RPC, subagents) it fails with omp's text
(`Tool "<t>" requires approval but no interactive UI available.` + options, or the restricted-folder
variant); a deny is `Tool "<t>" is blocked by user policy.` / `… by tool policy.\nReason: …`; a user
denial is `Tool call denied by user: <t>`. A prompt the mode raised can be approved "for this session"
(key = subject + tier). In `always-ask-cached`, a call with cache targets (the file, folder or search
tree it touches; public `http(s)` reads have none) offers grants instead: *Approve Directory* (the one
folder covering every target, listed in the prompt: up to 24 entries, 200 scanned), *Approve File* /
*Approve*, each "for this session" or, with the *Remember across sessions* toggle, in
`<agentDir>/approval-cache.json`. A grant covers its tier and the tiers below; a folder grant covers the
folder's own entries, never subfolders; a recursive search has its own tree key. `/forget-approvals`
clears every grant.

**ACP** (`modes/acp.c`, omp `#wrapToolForAcpPermission`): `bash` (resolved with `always-ask` unless the
yolo mode was configured explicitly or `--auto-approve` given) and edits that delete or move a file ask
the client with `session/request_permission` (`Allow once` / `Always allow` / `Reject` /
`Always reject`, title = the command's first 80 chars, `rawInput`, `$ <cmd>` content, absolute
locations); "always" answers persist per session and cache key; a client approval also satisfies the
inner gate. Rejections read `Tool call rejected by user (<t>)` (or `(preference)`).

Not ported: `bash.allowCompoundCommands` (per-segment `&&` chains), nested `xd://` dispatch prompts for
an explicit device policy, provider safety checks (computer use), extension `tool_approval_*` events,
the Cursor bridge's own approval path, RPC `extension_ui_request` prompts (RPC has no UI: prompts fail
like print mode; WP-15).

## Output capture and artifacts (`tools/outsink.c`, `tools/artifacts.c`)

These port omp's `OutputSink` (`tui/src/tools/streaming-output.ts`), `output-meta.ts` and
`session/artifacts.ts`, so bash, eval and read results are byte-identical to omp's:

- `sanitizeText`: UTF-8 repair, ANSI/OSC/DCS/APC stripping, C0/C1 removal, CR/CRLF → LF.
- Per-line cap `tools.outputMaxColumns` (768 bytes) with a `…` marker and an `artifact://N:raw:L-L`
  recovery notice.
- Head window `tools.artifactHeadBytes` plus a rolling tail within
  `tools.artifactSpillThreshold` (50 KB). The middle is elided as `[…Nln elided…]` with a
  `Read artifact://N for full output` notice.
- Artifacts are stored as `<session file minus .jsonl>/<id>.<tool>.log`, numbered per session and
  shared with subagents. Ids are allocated per bash/eval call. Files are capped at
  `tools.artifactMaxBytes`, and they are copied when a session is forked.
- `tool_postprocess_result()` (the `after_tool` hook) spills any oversized result from any tool
  the same way and writes omp's `details.meta`.

### Read page budget and the write projection guard

`read` pages through the budget of omp's `collectLineWindow`: `max(50 KB, lines * 512)`, capped by the spill threshold less
the row-prefix reserve. A numbered page charges a line cut to `tools.outputMaxColumns` the UTF-8 bytes of its cut display
(stray bytes count as 3-byte U+FFFD), `:raw` reads and a cap of `0` charge source bytes. A first line that neither form
fits gets the partial preview (`Showing line N (partial, …)`), or the "Hashline output requires full lines" refusal. A
leading context line that leaves no room for the requested line is dropped (retried from the requested start). The
column notice names the byte cap when the first cut line is larger than one raw read returns. Raw and
past-the-4-MiB-cap multi-range reads budget each range and append `[Range A-B stopped before line N at the … read budget.
Use :N-B to continue]`. omc holds the whole file in memory, so the streaming display-head logic of omp (`prefixLines`) has
no counterpart.

`write` refuses a payload that ends with a read notice when it would lose content (`read_projection_refusal`): a truncation
notice whose shown payload is shorter than the file, or any column-cap clause (a cut line ends in `…` in place of its tail).
Matching is exact (`out_is_column_truncation_notice`, `out_has_column_truncation_clause`): bracketed, with a stated cap and
unit.

### Job intents and captions

A bash job keeps the call's `i` intent as one line of plain text with home paths shortened (`job_clean_intent`). `/jobs`,
`/jobs full`, `proc://` listings, the wait card and `wait` results (omp `buildJobResult`: `## Completed`, `Intent:`,
`Label:`, `Delivery:`, `## Still Running`) lead with it ahead of the raw command line. The `Delivery:` line says how the
result reached the call: `delivered by this wait — it finished while you were waiting.` for a job that settled after
the call began, else `handed over by this snapshot (it finished <age> before this call) — this snapshot superseded its
queued completion push.` (settled jobs are delivered at the next turn boundary, so an earlier one always had its push
queued). `/jobs full` also asks the `widget`
role's model (role, then the `smol` defaults, first with a credential) for a one-line caption of each running command that
ran 15 s and needs explaining (`job_caption_needed`), at most two requests at once and once per job; the caption shows on a
later listing, under the intent, while `async.widgets` is on. omp also requests it when a job's widget is shown; omc has no
job widgets, so `/jobs full` is the only trigger. Requests are off-transcript `model_usage` entries, purpose `job-caption`.

## Eval kernel protocol (`tools/eval.c`, `assets/eval_kernel.py`)

The kernel is a persistent Python process started as `python3 -u -c <embedded source>` (interpreter
from `python.interpreter`, else `python3`/`python` on `PATH`). At startup it keeps private
duplicates of its stdin/stdout pipes for the protocol, points fd 0 at `/dev/null` and fd 1 at fd 2.
Anything user code, C extensions or subprocesses print lands on the stderr pipe, which the host
captures as raw cell output, so stray output can never corrupt the framing.

Newline-delimited JSON on the private channel:

```
kernel → host   {"type":"ready"}
                {"type":"call","id":M,"name":"read"|"__judge__"|…,"args":{…}}
                {"type":"cancel","id":M}
                {"type":"result","id":N,"stdout":"…","error":null|"…","images":[…]}
host → kernel   {"type":"exec","id":N,"code":"…"}
                {"type":"reply","id":M,"ok":true,"value":…} | {"type":"reply","id":M,"ok":false,"error":"…"}
```

- A host reader thread owns the read side. Each bridge `call` runs on its own worker thread, so
  concurrent helper calls (`asyncio.gather` over `judge()`) never block each other.
- `tool.<name>(...)` calls session tools. Session helpers go through `coding/evalhost.c`:
  `completion()` handles (default/smol/slow tiers, `schema` via a forced `respond` tool) with
  `wait()`/`.status`/`.cancel()`, `judge()` typed choice/bool/score answers (text judge with keyword
  prompts, `coding/judgment.c`, or native judgment APIs), `judge_batch()` host-owned async batches,
  `budget`, and `output()` over `agent://` outputs. Also `%load`, `%pip`, `%time`, `!cmd`, figures
  and printed images.
- `sh(command, cwd?, timeout?)` runs a command to completion on a persistent bash of the eval tool's own
  (`tools/eval.c` `__shell__`, apart from the bash tool's shell): output capped at 16 MiB, a non-zero
  exit or timeout raises `ShellError`.
- Interrupts (timeout or abort) send SIGINT and cancel the cell's in-flight calls. A kernel that
  doesn't answer within 5 s is killed. Waiting on helpers pauses the cell deadline.

omp's JS/Bun eval runtime and the `agent()`/`workpool()`/browser preludes are not implemented and are
not advertised in the description.

A kernel that died (crash, kill, out-of-memory, or a cancel/timeout that ended it) is replaced on the next call; the first
cell on the replacement opens with `Kernel restarted: the previous Python kernel is dead; state is unavailable. …`, once per
replacement. A `reset` gives no notice. `CompletionHandle.attempts` lists the candidates tried so far, without waiting:
`{model, effort, outcome, error?}`; omc tries one candidate (no completion fallback chain yet).

## MCP client (`src/mcp/`)

Subagents share the parent's connections, each with its own view of the tools (`agent_t.mcp_scope`,
`mcp_open_tool_scope`): a tool a server adds while a call to it runs reaches a session only once that session's own
call to the server completes (the call waits for the refresh it provoked, and the session re-registers its tools at the
next turn boundary). A new view starts from its spawner's. Tools present at connect, and tools a server adds while no
call to it runs, every session sees.

- Transports: stdio (`command` + `args`, a reader thread per server), streamable HTTP (`url`,
  `type: http|streamable-http`) and legacy SSE (`type: sse`). Protocol version `2025-06-18`.
- Config discovery (project first, then user; `mcp_discover_config`): `.omc/mcp.json`,
  `.omp/mcp.json`, `mcp.json`, `.mcp.json`, `.claude/mcp.json`, `.cursor/mcp.json`,
  `.vscode/mcp.json`, `<agent dir>/mcp.json`, `~/.cursor/mcp.json`, `~/.claude/mcp.json` and
  `~/.claude.json` (global and per-project `mcpServers`).
- Servers connect in parallel at session start (`mcp.startupTimeoutMs`). Their tools become
  `mcp__<server>_<tool>` (mounted under `xd://` by default) and their instructions are appended to
  the system prompt. Resources are read through `mcp://`. Subagents share the parent's connections.
- A failed tool call returns omp's `formatMCPToolFailure` block (`src/mcp/mcperr.c`, `mcp/errors.ts`): `MCP failure`,
  server, tool, transport, stage, failure class, retryable, the sanitized message, code, trace id, bounded and
  credential-redacted JSON-RPC `data`, and the next step. A retryable connection-class failure gets one reconnect and
  replay (`isRetriableConnectionError`); a stdio server that exits mid-call reports its exit code and is never replayed.
- OAuth for remote servers (`mcp/oauth.c`, port of `mcp/oauth-discovery.ts` and `oauth-flow.ts`):
  RFC 9728 resource metadata → RFC 8414/OIDC metadata → RFC 7591 dynamic registration (or a
  configured client) → authorization code + PKCE with the RFC 8707 `resource` indicator, through the
  shared login engine. Credentials are stored in `auth.json` under `mcp:<server url>` and refreshed
  automatically. Managed with `omc mcp list|login|logout` and `/mcp reauth|unauth`.
- `mcp.enableProjectConfig` (on) gates every project-level source; a server named in the user
  `mcp.json` `disabledServers` list or set `enabled: false` is not connected.
- Manager (`mcp.c`): servers are refcounted and named by the tool bridges, so `/mcp reload`,
  `reconnect`, `enable`/`disable` replace connections without invalidating tools in flight. Per
  server it keeps the initialize capabilities and serverInfo, the tool / prompt / resource / template
  catalogs, the connection state (connecting, connected, disconnected) and the subscribed URIs. A
  server still connecting after the startup window keeps connecting; its tools bind when it is ready.
- Tool cache (`toolcache.c`, port of `mcp/tool-cache.ts`; on for the session manager, off for ACP client
  servers like omp): every successful `tools/list` is stored in `<agent dir>/mcp-tool-cache.json` as
  `{"<server>": {version: 1, configHash, tools, expiresAt}}` (SHA-256 of the config's sorted-key JSON without
  omc's `_source`/`_provider` annotations, 30-day TTL, expired entries pruned on write). A server still
  connecting when the startup window closes gets its cached catalog as deferred tools (`cached_tools`,
  registered by `mcp_register_tools` like live ones): the bridge resolves the server by name, waits for the
  connection (`waitForConnection`, up to the server timeout, Esc aborts), tries one reconnect when it failed,
  then calls. The next tool sync swaps in the live catalog (`#replaceServerTools`); a reconnect with the same
  config keeps the cached catalog until then. The TUI shows omp's `xdev: xd://: mounted …` line for them
  at startup and the late `Connected to MCP server` status once the running turn's refresh settles.
- Print mode waits for MCP startup before the first turn (`mcp_wait_startup`, up to `OMP_MCP_TIMEOUT_MS`,
  default 30 s), binds the tools, and warns `MCP server "x" not ready after Nms` / `failed to connect: …;
  its tools are unavailable for this run.`; `OMP_MCP_REQUIRE_READY=1` exits 1 with
  `Error: MCP servers not ready: …` instead of prompting.
- Server notifications: `notifications/tools/list_changed`, `prompts/list_changed` and
  `resources/list_changed` re-list that catalog (on a worker thread); prompt changes show up in the
  MCP prompt commands immediately (ACP re-sends `available_commands_update`). With
  `mcp.notifications` on, every connected server that supports `resources.subscribe` is subscribed to
  its resources, and `notifications/resources/updated` for a subscribed URI is debounced
  (`mcp.notificationDebounceMs`) and delivered to the TUI session as omp's `[MCP notification] N
  resource(s) updated: …` user message (a follow-up while a turn runs, else a new turn).
- Config files (`mcpcfg.c`, port of `mcp/config-writer.ts`): the user file is `<agent dir>/mcp.json`,
  the project file `<cwd>/.omc/mcp.json`; atomic writes with `$schema` first; server-name and
  config validation with omp's messages. `/mcp add` (wizard or quick add), `remove`, `enable`,
  `disable`, `unauth` and `reauth` write them. omc keeps OAuth credentials url-keyed, so a signed-in
  server is saved without an `auth` block.
- `/mcp` in the TUI is `src/ui/mcpcmd.c` (+ the add wizard, `mcpwizard.c`); RPC/ACP use the text
  handlers in `src/coding/slashmcp.c` (one-off connections for `test`/`resources`/`prompts`).

## SSH hosts (`ssh.json`)

`tools/ssh.c` owns the `ssh.json` writer (`ssh_config_*`, port of `ssh/config-writer.ts`): user
`<agent dir>/ssh.json`, project `<cwd>/.omc/ssh.json`. `/ssh add|list|remove` (TUI: `ui/sshcmd.c`;
RPC/ACP: `coding/slashmcp.c`) and `omc ssh` share it; `ssh://` reads the same files plus the legacy
`ssh.json` / `.ssh.json` in the project root (listed as read-only "Discovered" hosts).

## LSP client (`src/lsp/lsp.c`)

JSON-RPC over stdio to language servers chosen by file type from `assets/lsp-servers.json` (omp's
definitions) merged with user `lsp.json`/`.lsp.json`/`lsp.yml`. Servers start lazily and are shared
with subagents. `lsp_after_write()` syncs written files and returns diagnostics, which are appended to
write results (`lsp.diagnosticsOnWrite`, on) and to edit results only with `lsp.diagnosticsOnEdit`
(off by default, like omp). The wait is `lsp.diagnosticsWaitMs`.
Timeouts follow omp's `resolveLspTimeouts`.
Both the LSP and DAP readers use `src/core/rpcframe.c` (omp `jsonrpc/message-framing.ts`): headers are capped at
16 KiB, exactly one numeric `Content-Length` up to 256 MiB is accepted, a header block without one is dropped as
stdout noise, and anything else ends the reader with a MessageFramingError ("LSP connection closed: …" / "DAP
connection closed: …" for the requests in flight).

## DAP client (`src/dap/dap.c`)

The `debug` tool drives one active Debug Adapter Protocol session (launch/attach, breakpoints,
stepping, stack, scopes, variables, evaluate, ...). Adapters come from
`assets/dap-adapters.json` plus the `debug.adapters` setting, and are selected by `fileTypes`. A
reader thread handles events. The e2e suite runs it against a scripted adapter
(`tests/e2e/mock_dap.py`).

## Adding a tool

1. Implement `agent_tool_t *tool_<name>_new(tool_env_t *)` in `src/tools/`. Use omp's description
   file via `tool_prompt()` and omp's exact schema via `schema_lit()`. Set `exclusive` if the tool
   mutates state.
2. Add it to `CTORS` and gating in `tools_common.c` (and `TOOL_META` for label/summary). Keep
   `BUILTIN_ORDER` canonical.
3. Report failures with `tool_result_error()` using omp's wording. Put renderer data in
   `details` in omp's shape so the TUI card (and omp's card on a shared session) render it.
4. Add a card renderer in `src/ui/tools/` ([tui.md](tui.md)), an e2e check in
   `tests/e2e/run.sh`, and a request-parity check if the wire changes.
5. Update [status.md](status.md) and this file.

### Images in `read`

Images are recognized by magic bytes (PNG, JPEG, GIF, WebP), never by extension (a `.png` holding text reads
as text). Files over 20 MB fail with `Image file too large: <size> exceeds 20.0MB limit.`; an image that does not
decode fails with `<path> is not a decodable <mime> image: Image: decode failed`. Otherwise the image is
normalized for the model when `images.autoResize` is on (default) and the result is the text note
`Read image file [<mime>]`, ` (displayed as <mime>)` when re-encoded, and on a size change
`[Image: original WxH, displayed at wxh. Multiply coordinates by S to map to original image.]`, followed by the
image block. Models without image input get `Image metadata:` (MIME, bytes, dimensions, channels, alpha)
instead. SVG rasterization (`:img`), HEIC/AVIF via ffmpeg, video frames and `?q=` image questions are not
implemented.
